# Action case work parts and procurement

## Model

- An action remains the customer-facing outcome. Existing actions do not acquire default work parts.
- Optional work parts divide an action by scope/trade, such as carpentry and painting.
- Cost lines remain the internal calculation. A line can belong to one work part within its own action.
- A request can include selected work across actions and work parts, with one recipient and one deduplicated set of attachments.
- New requests ask for a total per action/work part by default. Itemized pricing remains available.
- Preparing a request, recording a quote and selecting a quote in the calculation do not place an order.

## Editing

Direct quantities and rates can be edited without opening a quote editor. Changes require an explicit save. Bulk changes use an atomic database operation with the action's expected update timestamp. Failed saves retain the local inputs; stale updates must be retried after reloading the action.

Quoted and covered costs are not editable as independent hours or material. Remove the accepted price basis before modifying them. Internal calculations must be preserved when choosing another price basis and must never be added on top of a selected package price.

## Request snapshots

The request stores the selected action scopes, work part scopes, descriptions, requirements, files and final email body. A draft must be reviewed again when its source scope changes. Once sending has started, retries use the frozen email payload and its original idempotency key. Existing sent requests are not regenerated by this release.

File selection continues to use the action scope selection and existing attachment picker. It does not grant new portal access. Supplier response documents remain excluded from outgoing requests to other suppliers.

## Deployment

Apply the existing action-case foundation, files, costing, work quote and grouped-request migrations first, followed by the scope attachment migration and the new work-part/package migrations in filename order. Do not rerun older function-definition migrations after the new ones, since they may replace newer safeguards.

For this release, apply `db/2026-09-09_03_action_case_work_parts.sql` followed by `db/2026-09-09_04_action_case_package_pricing.sql` before enabling the new writes.

The new migrations are additive and rerunnable. Existing request presentation is retained as itemized; new requests explicitly choose grouped presentation. No production migration or real quotation email is sent by the local UI tests.

Independent group prices on one request are supported. A conditional price covering several groups must not be split into invented allocations: obtain independently orderable group prices before selecting them. The earlier calculation is restored when an accepted group price is removed. Historical supplier documents remain protected from individual deletion.

## Verification

Run the action-case Node tests, TypeScript checking and `scripts/test-action-case-costing-ui.mjs`. The UI harness runs the production components with synthetic data and local assets at desktop and mobile widths. Database tests exercise tenant boundaries, atomic updates, stale data and immutable request snapshots separately from the UI harness.
